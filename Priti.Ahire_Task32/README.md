# To-Do List Application - REST API Design

## 1. Project Overview

This project is a beginner-friendly API design for a To-Do List application. The goal is to define a clean and RESTful way to manage tasks such as creating new tasks, viewing all tasks, viewing a single task, updating task details, and deleting tasks.

This task focuses on API design and documentation only. It does not build a complete backend or frontend application.

## 2. API Design

The API follows RESTful principles. In REST, each important object is treated as a resource. In this application, a task is the main resource.

The API uses:

- Resource-based URLs such as `/api/tasks`
- Standard HTTP methods like `GET`, `POST`, `PATCH`, and `DELETE`
- JSON for request and response bodies
- Meaningful HTTP status codes

## 3. Task Resource

A task is represented as a JSON object with the following fields:

```json
{
  "id": 1,
  "title": "Complete assignment",
  "description": "Finish the API documentation",
  "completed": false,
  "createdAt": "2026-10-06T10:00:00Z",
  "updatedAt": "2026-10-06T10:00:00Z"
}
```

### Field Explanation

- `id`: A unique number or identifier used to identify one task.
- `title`: Short name of the task.
- `description`: More detail about what the task needs.
- `completed`: Shows whether the task is finished or not. It is a boolean value (`true` or `false`).
- `createdAt`: The date and time when the task was created.
- `updatedAt`: The date and time when the task was last updated.

Important note: the client should not manually generate the task ID. The backend or database should generate it automatically so that each task gets a unique identifier.

## 4. API Endpoints

| Operation | HTTP Method | Endpoint | Purpose |
|---|---|---|---|
| Create task | POST | `/api/tasks` | Add a new task |
| Read all tasks | GET | `/api/tasks` | Get all tasks |
| Read one task | GET | `/api/tasks/:id` | Get a specific task |
| Update task | PATCH | `/api/tasks/:id` | Partially update a task |
| Delete task | DELETE | `/api/tasks/:id` | Remove a task |

## 5. CRUD Operations

### CREATE

`POST /api/tasks`

Used to add a new task.

### READ

- `GET /api/tasks` to view all tasks.
- `GET /api/tasks/:id` to view one specific task.

### UPDATE

`PATCH /api/tasks/:id`

Used to modify one or more fields of an existing task without replacing the whole object.

### DELETE

`DELETE /api/tasks/:id`

Used to remove a task permanently.

## 6. HTTP Status Codes

The API uses standard HTTP status codes, including:

- `200 OK`: Request successful.
- `201 Created`: A new task was successfully created.
- `204 No Content`: A task was successfully deleted.
- `400 Bad Request`: Invalid request data or validation failure.
- `404 Not Found`: The requested task does not exist.
- `500 Internal Server Error`: The server had an unexpected problem.

## 7. Validation

Basic validation rules include:

- `title` is required.
- `title` cannot be empty.
- `completed` must be a boolean value (`true` or `false`).
- `id` must uniquely identify a task.
- IDs should be generated by the server or database.

If validation fails, the API should return `400 Bad Request` with a clear error response.

## 8. Error Handling

The frontend should be able to understand the API error response so it can show a useful message to the user.

Examples include:

- `400 Bad Request` when the request data is invalid.
- `404 Not Found` when a task ID is not found.
- `500 Internal Server Error` when the server fails unexpectedly.

## 9. Potential Challenges

Some common challenges in a To-Do application include:

- Input validation
- Unique task IDs
- Task not found errors
- Data persistence in a database
- Concurrent updates if multiple users edit the same task
- Proper error handling
- Authentication or authorization for multiple users
- Frontend-backend integration
- Invalid request data
- Server or database failures
