# To-Do List Application - API Documentation

## 1. Introduction

This document describes a simple RESTful API for a To-Do List application. The application allows users to create tasks, view all tasks, view a single task, update task information, and delete tasks.

The focus of this task is API design and documentation, not backend implementation. This means the document explains how the application should behave, what endpoints should exist, and what responses should be returned.

## 2. Objectives

The main objectives of this API are to:

- allow users to add new tasks
- retrieve all tasks
- retrieve a single task by ID
- update selected fields of a task
- delete a task
- handle errors clearly and consistently
- follow RESTful API design principles

## 3. REST API Overview

REST is a style of designing APIs where resources are represented using URLs and standard HTTP methods are used to perform operations on those resources.

In this project:

- A task is the main resource.
- The resource is represented by the endpoint `/api/tasks`.
- Each task has a unique ID.
- `GET`, `POST`, `PATCH`, and `DELETE` are used to work with the resource.

## 4. Task Data Model

A task resource should look like this:

```json
{
  "id": 1,
  "title": "Complete assignment",
  "description": "Finish the API documentation",
  "completed": false,
  "createdAt": "2026-10-06T10:00:00Z",
  "updatedAt": "2026-10-06T10:00:00Z"
}
```

### Field Description

| Field | Type | Description |
|---|---|---|
| `id` | integer/string | A unique identifier for the task. It should be generated by the backend or database, not manually by the client. |
| `title` | string | The short name or heading of the task. |
| `description` | string | Extra detail about the task. |
| `completed` | boolean | Indicates whether the task is completed. |
| `createdAt` | string | Date and time when the task was created. |
| `updatedAt` | string | Date and time when the task was last updated. |

### Important Note on ID Generation

The client should not manually create the task ID. The backend or database should generate a unique ID automatically. This prevents duplicate IDs and ensures each task can be accessed uniquely.

A unique ID can be:

- an integer such as `1`, `2`, `3`
- a UUID such as `a7c6b1d0-18e3-4d08-b8e2-aa1234bb5678`

Example UUID:

```json
"id": "a7c6b1d0-18e3-4d08-b8e2-aa1234bb5678"
```

## 5. API Endpoint Summary

| Operation | HTTP Method | Endpoint | Purpose |
|---|---|---|---|
| Create task | `POST` | `/api/tasks` | Add a new task |
| Get all tasks | `GET` | `/api/tasks` | Retrieve all tasks |
| Get one task | `GET` | `/api/tasks/:id` | Retrieve one task by ID |
| Update task | `PATCH` | `/api/tasks/:id` | Modify one or more task fields |
| Delete task | `DELETE` | `/api/tasks/:id` | Remove a task |

## 6. Create Task API

### Endpoint

`POST /api/tasks`

### Purpose

Create a new task in the application.

### Path Parameters

No path parameter is required for this endpoint.

### Request Body

```json
{
  "title": "Complete assignment",
  "description": "Finish the API documentation",
  "completed": false
}
```

### Example Request

```http
POST /api/tasks
Content-Type: application/json

{
  "title": "Complete assignment",
  "description": "Finish the API documentation",
  "completed": false
}
```

### Example Success Response

```json
{
  "id": 1,
  "title": "Complete assignment",
  "description": "Finish the API documentation",
  "completed": false,
  "createdAt": "2026-10-06T10:00:00Z",
  "updatedAt": "2026-10-06T10:00:00Z"
}
```

### Success Status Code

`201 Created`

### Error Cases

- Missing or empty `title`
- Invalid `completed` type
- Server/database failure

### Error Response Example

```json
{
  "error": "Title is required"
}
```

### Error Status Code

`400 Bad Request`

### Reasoning

`POST` is used because we are creating a new resource. The API should return `201 Created` when a task is successfully added.

## 7. Get All Tasks API

### Endpoint

`GET /api/tasks`

### Purpose

Retrieve all tasks.

### Path Parameters

No path parameter is required.

### Request Body

No request body is required.

### Example Request

```http
GET /api/tasks
```

### Example Success Response

```json
[
  {
    "id": 1,
    "title": "Complete assignment",
    "description": "Finish the API documentation",
    "completed": false,
```

## 9. Update Task API

### Endpoint

`PATCH /api/tasks/:id`

Example:

`PATCH /api/tasks/1`

### Purpose

Update one or more fields of an existing task.

### Path Parameters

| Name | Type | Description |
|---|---|---|
| `:id` | integer/string | The unique ID of the task to update. |

### Request Body

```json
{
  "title": "Complete API assignment",
  "completed": true
}
```

### Example Request

```http
PATCH /api/tasks/1
Content-Type: application/json

{
  "title": "Complete API assignment",
  "completed": true
}
```

### Example Success Response

```json
{
  "id": 1,
  "title": "Complete API assignment",
  "description": "Finish the API documentation",
  "completed": true,
  "createdAt": "2026-10-06T10:00:00Z",
  "updatedAt": "2026-10-06T10:18:00Z"
}
```

### Success Status Code

`200 OK`

### Error Cases

- Task does not exist
- Invalid field values
- Missing or incorrect data type
- Server failure

### Error Response Example

```json
{
  "error": "Task not found"
}
```

### Error Status Code

`404 Not Found`

### Reasoning

`PATCH` is used when we want to modify only some fields of an existing task. It is more appropriate than requiring the whole task object because the client may only want to change one or two fields, such as `title` or `completed`.

### Path Parameters

| Name | Type | Description |
|---|---|---|

### Request Body

No request body is required.

### Example Request

```http
DELETE /api/tasks/1
```

### Example Success Response

No response body is usually sent.

### Success Status Code

`204 No Content`

### Error Cases

- Task does not exist
- Server failure

### Error Response Example

```json
{
  "error": "Task not found"
}
```

### Error Status Code

`404 Not Found`

### Reasoning

`DELETE` is appropriate because the purpose is to remove a resource from the system. A successful delete often returns `204 No Content` because there is no content to send back.

## 11. CRUD Operations

The CRUD process in this To-Do application is as follows:

### CREATE

- `POST /api/tasks`
- Adds a new task to the list

### READ

- `GET /api/tasks` fetches all tasks
- `GET /api/tasks/:id` fetches one task by its unique ID

### UPDATE

- `PATCH /api/tasks/:id` updates one or more fields in the task

### DELETE

- `DELETE /api/tasks/:id` removes a task

### How the APIs Work Together

The frontend or client sends requests to the API. For example:

1. Create a task with `POST /api/tasks`
2. Fetch all tasks with `GET /api/tasks`
3. Open one task with `GET /api/tasks/:id`
4. Change a field with `PATCH /api/tasks/:id`
5. Remove the task with `DELETE /api/tasks/:id`

This is the normal flow for a task management application.

## 12. HTTP Status Codes

Here are the most relevant HTTP status codes for this API:

| Status Code | Meaning | When to Use It |
|---|---|---|
| `200 OK` | Request succeeded | Used for successful `GET` and `PATCH` responses |
| `201 Created` | A resource was created | Used after successful `POST` operation |
| `204 No Content` | Request succeeded with no body returned | Used after successful `DELETE` |
| `400 Bad Request` | Client sent invalid data | Used when required fields are missing or values are wrong |
| `404 Not Found` | Resource was not found | Used when the task ID does not exist |
| `500 Internal Server Error` | Server error | Used when something unexpected happens on the server |

Not every API must return every status code. The API should return only the status that matches the result of the request.

## 13. Validation Rules

Basic validation rules for the To-Do List API include:

- `title` is required
- `title` cannot be empty
- `completed` must be a boolean value (`true` or `false`)
- `id` must uniquely identify a task
- `server/database generates the ID`

### Example Validation Error

```json
{
  "error": "Title is required"
}
```

### HTTP Status for Validation Failure

`400 Bad Request`

When validation fails, the server should reject the request and explain what is wrong.

## 14. Error Handling

The API should return clear error messages so the frontend can understand what went wrong.

### 400 Bad Request

Used when the client sends invalid data.

Example:

```json
{
  "error": "Title cannot be empty"
}
```

### 404 Not Found

Used when the requested task does not exist.

Example:

```json
{
  "error": "Task not found"
}
```

### 500 Internal Server Error

Used when the server fails unexpectedly.

Example:

```json
{
  "error": "Internal server error"
}
```

The frontend should be able to read these error responses and show simple user-friendly messages such as "Task not found" or "Please enter a title".

## 15. Unique ID Generation

Each task must have a unique ID. Without a unique ID, the system cannot reliably identify which task to update or delete.

### Why the Client Should Not Assign IDs

The client should not manually generate the task ID because:

- two clients could create the same ID by mistake
- it can lead to conflicts
- the backend needs control over uniqueness

### Why the Backend or Database Should Generate IDs

The backend or database should generate unique IDs automatically. This guarantees that each task is unique and prevents duplicates.

### Integer ID or UUID

Either of these can be used:

- integer ID: `1, 2, 3`
- UUID: `a7c6b1d0-18e3-4d08-b8e2-aa1234bb5678`

Example UUID:

```json
"id": "a7c6b1d0-18e3-4d08-b8e2-aa1234bb5678"
```

## 16. REST Design Reasoning

This design follows REST principles in a beginner-friendly way.

### Resources

A task is a resource. The API works with tasks as objects.

### Resource-Based URLs

The task resource is accessed through URLs like `/api/tasks` and `/api/tasks/:id`.

### HTTP Methods

Different HTTP methods are used for different actions:

- `POST` to create
- `GET` to read
- `PATCH` to update
- `DELETE` to remove

### Stateless Requests

Each request should contain the information needed to process it. The server does not need to remember previous requests in order to handle the next one.

### Meaningful HTTP Status Codes

The API uses proper status codes like `200`, `201`, `204`, `400`, `404`, and `500` so the client can understand success or failure clearly.

### Path Parameters

The `:id` in `/api/tasks/:id` is a path parameter. It represents the unique ID of the task being accessed.

### JSON Request and Response Bodies

The API sends and receives JSON data. This makes it easy for web applications and mobile apps to communicate with the server.

### Consistent Endpoint Naming

The endpoint naming is clear and consistent across the API:

- `/api/tasks` for the task collection
- `/api/tasks/:id` for one task

This makes the API easier for developers to understand and maintain.

## 17. Potential Implementation Challenges

Here are common implementation challenges for this type of application:

1. Input validation: making sure required fields such as `title` are present and valid.
2. Unique task IDs: ensuring no two tasks share the same ID.
3. Task not found: handling missing tasks when updating or deleting.
4. Database/data persistence: saving tasks so they remain available after refresh or server restart.
5. Concurrent updates: what happens when two users update the same task at the same time.
6. Error handling: returning clear and consistent error messages.
7. Authentication/authorization: controlling which users can create, edit, or delete tasks.
8. Frontend-backend integration: making sure the frontend can correctly use the API.
9. Invalid request data: making sure the server rejects bad JSON or wrong field types.
10. Server/database failures: handling unexpected issues without crashing the application.

## 18. Conclusion

This To-Do List API design follows RESTful principles and uses the standard CRUD flow:

- Create: `POST /api/tasks`
- Read all: `GET /api/tasks`
- Read one: `GET /api/tasks/:id`
- Update: `PATCH /api/tasks/:id`
- Delete: `DELETE /api/tasks/:id`

This structure is easy to understand, easy to maintain, and suitable for a beginner-friendly To-Do application.

The design emphasizes clear endpoints, meaningful status codes, consistent JSON structures, and proper validation and error handling.
